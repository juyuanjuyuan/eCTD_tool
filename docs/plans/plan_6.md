# Plan 6 — WP-06: eCTD 文件管理、命名规范与版本控制

## 目标

实现符合 eCTD 文件规范的完整文件管理功能: 严格的文件命名规则、存储路径规范、文件复用机制、PDF 直接上传（非编辑器内容）的合规检查、以及跨序列文件引用管理。

## 前置依赖

- Plan 3 完成（编辑器可用）
- MinIO 服务已就绪 (Plan 1 Docker)

## 阶段 1: eCTD 文件命名与路径规范

### 1.1 文件命名规则（技术规范 3.3.2）
系统必须强制执行 eCTD 文件命名规范:
- [x] **允许字符**: 小写字母 a-z、数字 0-9、连字符 -、下划线 _
- [x] **不允许**: 空格、中文字符、大写字母、其他特殊字符
- [x] **路径规则**: 仅使用正斜杠 /（不允许反斜杠 \）
- [x] **长度限制**:
  - 从序列文件夹开始的完整路径（含扩展名）≤ 180 字符
  - 单个文件夹或文件名（含扩展名）≤ 64 字符
- [x] 创建 `FileNameNormalizer` 服务:
  ```typescript
  // 自动转换用户上传的文件名为 eCTD 合规格式
  function normalizeFileName(name: string): string {
    return name
      .toLowerCase()
      .replace(/[^a-z0-9\-_\.]/g, '-')  // 非法字符替换为连字符
      .replace(/-+/g, '-')               // 合并连续连字符
      .replace(/^-|-$/g, '');            // 去除首尾连字符
  }
  ```
- [x] 文件名转换后检查长度限制
- [x] 原始文件名保留在数据库（用于显示），存储路径使用转换后的合规名

### 1.2 文件存储路径规范（技术规范表 5）
- [x] 目录结构严格遵循 eCTD 规范:
  ```
  {申请编号}/                          # 由申请编号命名
  └── {序列号4位}/                     # 如 0000, 0001
      ├── m1/cn/{章节号}/              # 模块一: m1/cn/00/, m1/cn/02/ ... m1/cn/12/
      ├── m2/{ICH子目录}/              # 模块二: m2/22-intro/, m2/23-qos/ 等
      ├── m3/{ICH子目录}/              # 模块三: m3/32-body-data/, m3/33-lit-ref/
      ├── m4/{ICH子目录}/              # 模块四: m4/42-stud-rep/, m4/43-lit-ref/
      └── m5/{ICH子目录}/              # 模块五: m5/52-tab-list/ 等
  ```
- [x] 模块一章节号与文件夹的映射:
  - cn-1-0 → 00/, cn-1-2 → 02/, cn-1-3 → 03/, ..., cn-1-12 → 12/
  - 注意: 没有 01/ 文件夹（跳过）
- [x] MinIO 存储路径: `{project_id}/{application_number}/{sequence_number}/m{module}/{folder}/{filename}`

### 1.3 允许的文件类型（技术规范 3.3.1）
- [x] 仅允许 5 种文件扩展名:
  - `.pdf` — 审评内容文件（最主要格式）
  - `.xml` — eCTD 骨架文件、STF 文件
  - `.xpt` — SAS XPORT 传输文件（临床试验数据）
  - `.txt` — 程序代码文件
  - `.xsl` — XML 样式文件
- [x] 上传时验证文件扩展名
- [x] 拒绝不在列表中的文件类型

## 阶段 2: MinIO 文件存储与上传

### 2.1 MinIO 集成
- [x] 安装 MinIO SDK (`minio`)
- [x] 创建 `FileModule` / `FileService`
- [x] MinIO Bucket 管理
- [x] 文件上传（multipart/form-data，限制 200MB）
- [x] 文件下载（presigned URL，有效期 1h）
- [x] 文件预览（presigned URL）
- [x] 文件删除

### 2.2 上传 API
- [x] POST `/api/v1/nodes/:nodeId/files/upload`
  - 支持单文件/多文件上传
  - 上传时自动:
    1. 验证文件扩展名（仅允许 .pdf/.xml/.xpt/.txt/.xsl）
    2. 验证文件大小（普通文件≤200MB，SAS XPT≤4GB）
    3. 转换文件名为 eCTD 合规格式
    4. 计算 MD5 哈希值
    5. 检查路径长度（≤180 字符）
  - 返回文件元数据（含 MD5、合规文件名、存储路径）

### 2.3 文件管理 API
- [x] GET `/api/v1/nodes/:nodeId/files` — 文件列表
- [x] GET `/api/v1/nodes/:nodeId/files/:id` — 文件详情
- [x] DELETE `/api/v1/nodes/:nodeId/files/:id` — 删除文件
- [x] GET `/api/v1/nodes/:nodeId/files/:id/download` — 下载
- [x] GET `/api/v1/nodes/:nodeId/files/:id/preview` — 预览

### 2.4 PDF 自动分析
- [x] 上传 PDF 时自动分析并存储:
  - PDF 版本号
  - 页数
  - 是否有书签（>5页时必须有）
  - 是否加密
  - 是否有外部链接
  - 是否有 JavaScript
  - 是否有附件/嵌入式文件
  - 是否有音频/视频/3D 对象
  - 字体信息（是否嵌入）
  - 文本是否可搜索
  - 书签放大率是否为 Inherit Zoom
- [x] 分析结果对照验证标准 6.x 标注合规/警告/错误
- [x] 不合规的 PDF 提供修复建议

## 阶段 3: 文件复用（技术规范 3.3.4）

### 3.1 文件引用规则
- [x] 文件复用包括两种情况:
  1. **同一序列内复用**: 同一序列中不同章节引用同一文件（骨架文件中多个叶元素指向同一路径）
  2. **跨序列复用**: 引用同一申请中前序序列的文件（骨架文件中叶元素的 xlink:href 指向前序序列路径）
- [x] **不支持跨申请引用**: 不允许引用另一个申请中提交的文件
- [x] 跨序列引用时:
  - 仅允许引用已提交（非草稿）的前序序列内容
  - 引用而非复制: 骨架文件中 xlink:href 指向原文件的相对路径
  - 无需重复提交实体文件
  - 引用的文件必须在前序序列中确实存在

### 3.2 前端引用管理
- [x] 文件引用选择器: 选择同一申请内其他序列的已有文件
- [x] 引用文件预览
- [x] 引用关系可视化（哪些章节引用了同一文件）
- [x] 引用验证: 确保引用的文件在前序序列中存在

## 阶段 4: 空缺章节处理（技术规范 3.3.3）

### 4.1 空缺章节规则
- [x] **不允许空文件夹**: 序列中不允许存在没有文件或子文件夹的文件夹
- [x] **不允许占位文档**: 不允许提交没有实际内容的文档
- [x] 对于不适用的章节:
  - 不在 eCTD 包中创建该章节的文件夹
  - 不在骨架文件中创建该章节的目录元素
  - 在模块一的说明函中说明哪些章节不适用及原因
- [x] 系统在导出 eCTD 包时自动过滤空章节
