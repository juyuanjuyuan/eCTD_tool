# Plan 8 — WP-08: eCTD 合规测试、CDE 验证对齐与部署

## 目标

完成端到端测试，**重点是 eCTD 合规性测试**: 生成的 eCTD 提交包必须通过 CDE 官方验证软件 V1.1.0 的全部错误级别检查。测试覆盖各种申请类型、生命周期场景和边界情况。

## 前置依赖

- Plan 1-7 全部完成

## 阶段 1: eCTD 合规测试（最高优先级）

### 1.1 CDE 官方验证软件对齐
- [ ] 下载并安装 CDE eCTD 验证软件 V1.1.0
- [ ] 建立自动化测试流程:
  1. 系统生成 eCTD 包 → 2. 使用 CDE 验证软件验证 → 3. 对比结果
- [ ] 确保系统内置验证引擎与 CDE 验证软件结果一致
- [ ] 记录所有差异并调整系统验证规则

### 1.2 按申请类型的完整测试矩阵
- [ ] **临床试验申请 (cnapt1) + 首次申请 (cnrat1)** — 完整 eCTD 包生成与验证
- [ ] **新药申请 (cnapt2) + 首次申请 (cnrat1)** — 最完整场景（覆盖最多章节）
- [ ] **新药申请 (cnapt2) + 补充申请 (cnrat2)** — 含 replace/delete 操作
- [ ] **仿制药申请 (cnapt3) + 首次申请 (cnrat1)** — 简化版目录
- [ ] **仿制药申请 (cnapt3) + 再注册 (cnrat8)** — 最少章节场景
- [ ] **原料药申请 (cnapt4) + 首次申请 (cnrat1)** — V1.1 新增类型
- [ ] 每种场景验证:
  - 内容完整性规则 (4.3.x) 正确执行
  - 必填章节全部存在
  - 信封元素正确
  - 受控词汇代码正确使用
  - 文件命名合规
  - PDF 文件合规

### 1.3 生命周期场景测试
- [ ] **场景 1**: 首次提交 (0000) → 全部 new 操作
- [ ] **场景 2**: 首次提交 (0000) → 回复序列 (0001) → 包含 replace 操作
- [ ] **场景 3**: 多序列累积 → 0000 → 0001 (replace) → 0002 (delete 部分 + new 部分)
- [ ] **场景 4**: 撤回序列 → 验证 4 步撤回流程自动生成正确
  - 原 new → delete
  - 原 replace → 恢复原文件 (new)
  - 原 delete → 重新创建 (new)
  - 模块四五 STF 同步处理
- [ ] **场景 5**: 格式转换序列 (cnsqt4) → 验证转换规则
- [ ] **场景 6**: 文件复用 → 同一申请跨序列引用
- [ ] **场景 7**: 骨架属性更新 → 删除旧 2.3.S/3.2.S 重建验证
- [ ] 每个场景的 modified-file 属性正确性验证

### 1.4 边界情况测试
- [ ] 200MB 接近上限的 PDF 文件
- [ ] 路径长度接近 180 字符上限
- [ ] 超过 5 页和不超过 5 页的 PDF 书签规则
- [ ] 包含外文参考资料的 xml:lang 处理
- [ ] 扩展节点（仅生物制品 3.2.R 章节）
- [ ] 空章节过滤（确保不生成空文件夹）
- [ ] 大量叶元素（200+ 个文件的序列）
- [ ] STF 的 category 和 file-tag 全部使用 valid-values.xml 中的值

### 1.5 XML 骨架验证测试
- [ ] index.xml DTD 验证（每次生成自动验证）
- [ ] cn-regional.xml Schema 验证
- [ ] STF 文件 DTD 验证
- [ ] index-md5.txt 校验值一致性
- [ ] 所有叶元素的 checksum 与实际文件 MD5 一致
- [ ] 叶元素 ID 唯一性和格式（不以数字开头）
- [ ] xlink:href 路径正确（相对路径、正斜杠、指向存在的文件）
